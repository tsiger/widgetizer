# Theme structure and lifecycle

Rule labels are defined in `SKILL.md`. This reference covers package acceptance, source ownership, manifest settings, and updates.

## Package acceptance versus a functioning theme

**Enforced by theme ZIP upload:** one consistent root folder; safe archive paths; root `theme.json`, `layout.liquid`, and `screenshot.png`; entries beneath `assets/`, `templates/`, and `widgets/`; parseable manifest JSON; truthy `name`, `version`, and `author`; accepted version syntax; valid effective collection definitions when present. An update import validates the merged collection definitions, not only the incoming files.

The directory checks use archive-entry prefixes. They are not exhaustive checks that those folders contain working assets, pages, or widgets. Author real files rather than depending on empty ZIP-directory entries.

Version syntax is `digits.digits.digits`, for example `1.0.0`. The current parser does not support `v1.0.0`, prerelease suffixes, or build metadata. Use conventional numeric releases without leading zeros.

**Contract:** a usable theme also needs valid widget schemas/templates, renderable starter pages, all referenced assets/snippets, and a layout that emits its content. Every advertised feature must work in the editor and export. Import acceptance alone proves none of these.

**Convention:** provide a real 1280 x 720 PNG screenshot and `locales/en.json` (at least `{}` for a theme with direct labels, no global setting groups, and no theme-owned visitor words). ZIP upload checks the screenshot's presence, not its dimensions, and does not require locales. The repository locale validator does require the locale directory, English file, and `global.<group>.name` entries for any global setting groups. See localization for a matching example.

## Authored files

```text
my-theme/
  theme.json
  layout.liquid
  screenshot.png
  assets/
    base.css
  widgets/
    intro/
      schema.json
      widget.liquid
    global/                 optional global widget definitions
      header/
        schema.json
        widget.liquid
      footer/
        schema.json
        widget.liquid
  templates/
    index.json
    global/                 when providing global starter instances
      header.json
      footer.json
  locales/
    en.json
  snippets/                 optional reusable Liquid partials
  menus/                    optional starter menus
  collection-types/         optional theme-owned content definitions
  presets/                  optional creation-time variants
  updates/                  optional released deltas
```

Use a stable lowercase hyphenated theme folder ID by convention; it is distinct from the display name. Paths and filename case must work on case-sensitive systems. Do not ship a project backup as a theme ZIP.

`latest/` is generated by layering the base and updates in numeric version order. Do not author it or rely on a hand-edited snapshot being retained. Do not put build tools, dependency trees, private material, or development artifacts inside the distributable theme root: project creation copies most root contents.

## Manifest and theme settings

Minimal metadata:

```json
{
  "name": "My Theme",
  "version": "1.0.0",
  "author": "Theme Author",
  "description": "An independently designed Widgetizer theme",
  "useCoreWidgets": true,
  "settings": {
    "global": {
      "colors": [
        { "id": "background", "type": "color", "label": "Background", "default": "#ffffff", "outputAsCssVar": true }
      ]
    }
  }
}
```

**Contract:** `settings.global` maps group names to arrays of setting definitions. Group names are flexible. Values reach Liquid as `theme.<group>.<id>`. The schema's `default` supplies initial/fallback data; an installed project's `value` takes precedence when defined, including `false`, `0`, and `""`. Author source defaults; do not copy a user's `value` entries into a new distribution.

Keep setting IDs unique within their scope. **Convention:** make global IDs unique across groups as well, because preset overrides are a flat ID-to-value map and can otherwise affect multiple groups.

`{% theme_settings %}` emits `--<group>-<id>` only for settings with `outputAsCssVar: true`, plus automatic font-picker variables. It processes global theme settings, not arbitrary widget settings. It does not turn an image path into `url(...)` or load a font merely because a CSS value names one.

- A numeric `range` with `unit` receives that unit in the generated CSS value.
- A `font_picker` emits `--<group>-<id>-family` and `--<group>-<id>-weight` without `outputAsCssVar`. Use its `{ "stack": "...", "weight": 400 }` value shape.
- `{% fonts %}` reads font pickers specifically from `settings.global.typography`. Its Bunny Fonts switch is specifically `settings.global.privacy` / `use_bunny_fonts`; moving this setting into another group does not configure that tag.
- Custom code tags look specifically in `settings.global.advanced` for `custom_css`, `custom_head_scripts`, and `custom_footer_scripts`.
- Optional `settings.imageSizes` replaces the app image-size configuration rather than extending it. Use size-name keys with `width`, `enabled`, and optional `quality`; the media system still generates its library thumbnail. Check the media pipeline before depending on a custom derivative.

These special group names are feature contracts; Arch's other group names and token system are not required.

## Core and global widgets

Core currently supplies `core-spacer`, `core-divider`, and `core-form`. They are included unless `useCoreWidgets` is explicitly `false`. `core-` is a reserved resolution path, not a theme override mechanism. If opting out, implement whatever replacements the theme actually needs; copying a core filename into the theme does not override core rendering.

The types `header` and `footer` resolve under `widgets/global/<type>/`. Their starter instances belong under `templates/global/`. They are not ordinary page widget directories. A theme can omit global content, but if it supplies it, the layout must emit it. A theme with a header/footer is not required to reproduce Arch's controls or block types.

## Three copies and the authoring loop

1. Maintained theme source, for example the repository's `themes/<id>/`.
2. Installed theme library, normally `data/themes/<id>/` in the local app; an effective `latest/` snapshot wins when it contains `theme.json`.
3. Installed project copy, with its own theme files, settings, and authored content.

Editing one copy does not automatically update the others. Locate the actual target from the current task/environment; do not hardcode a desktop profile directory. Create or use a disposable project for verification. Theme/preset synchronization helpers can mutate projects: inspect their scope and use them only for an intended test target.

Project creation excludes templates from the general copy and instantiates them into pages separately. `updates/`, `latest/`, `presets/`, and `preset-media/` are excluded from the project copy. Presets are consumed once; subsequent preset edits do not restyle existing projects.

## Distributed updates

**Enforced:** each `updates/<version>/` has an accepted numeric version and a parseable `theme.json` whose `version` exactly matches the folder. Re-uploading an installed theme imports new update versions; its base version must match the installed base. Merely changing the base files is not an update delivery mechanism.

**Contract:** preserve the released base for ZIP updates. Add a new delta folder with the changed files and the new manifest. Include the full intended manifest/settings schema; do not assume a manifest containing only `version` is a usable replacement. Generate/rebuild `latest/` through the application mechanism.

At project update:

- Theme infrastructure (`layout.liquid`, `assets`, `widgets`, `snippets`, `locales`, `screenshot.png`, `collection-types`) is refreshed.
- Matching customized settings are preserved; new settings get defaults; removed definitions are dropped. Moving a setting between groups is not a transparent rename.
- Existing pages, uploaded media, and collection item data are protected. Missing starter pages/menus can be added; existing content is preserved.
- Changes to collection definitions can leave archived or newly required fields. A theme update does not automatically migrate arbitrary item schemas or translate content.

Deletion markers under `updates/<version>/deleted/` mirror target paths. A placeholder file deletes that file; an empty marker directory deletes the corresponding directory; nonempty directories are path containers. Do not delete a widget/block definition still used by existing content unless the requested migration handles those instances.

An unrelated theme switch is a separate migration problem. Matching widget names or roles does not prove content compatibility.
